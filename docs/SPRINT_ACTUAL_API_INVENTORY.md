### Mismatched Request/Response Schemas

1. **POST /api/v1/chat/** — Request uses `ChatRequest` schema (with `project_id` field), but the function body reads `data.project_id` from the ChatRequest and passes it to `process_chat`. The `ChatResponse` model has many optional fields (retrieval_method, retrieval_sources, latency_ms, confidence, provider) that are populated by the orchestrator. This is consistent.

2. **POST /api/v1/workspace/** (update_workspace) — Request body is `dict` (raw), not a Pydantic model. The allowed fields are {name, description, slug, perm_join, perm_member_manage}. This is a loose schema — any JSON body is accepted, only whitelisted keys are applied.

3. **POST /api/v1/memory/search** — Request is `MemorySearchRequest` (body), but the frontend sends `{ query, limit, project_id }` as body. The backend `MemorySearchRequest` schema does NOT have `project_id` field. The backend function signature takes `project_id` from `TenantContext`, not from the request body. **The frontend sends `project_id` in the body but the backend ignores it.** The actual project_id comes from the tenant context.

4. **GET /api/v1/ingest/graph** — The frontend `useGraph.ts` calls `/api/v1/graph` but the backend route is `/api/v1/ingest/graph`. **This is a frontend bug — the URL is wrong.**

5. **GET /api/v1/ingest/search** — The frontend `search/page.tsx` calls `/api/v1/search` but the backend route is `/api/v1/ingest/search`. **This is a frontend bug — the URL is wrong.**

6. **GET /api/v1/ingest/jobs** — The frontend expects `IngestJobOut[]` as the response, but the backend returns `{"items": [...], "total": N}` (a dict, not an array). **This is a type mismatch.**

7. **POST /api/v1/ingest/upload** — The frontend `uploadFile()` function sends `project_id` and `source_type` as FormData fields plus a `file` field. The backend expects `IngestUploadRequest` (JSON body with `project_id`, `source_type`, `title`, `content`, `config`). The frontend uses XHR with FormData multipart, while the backend route is declared as accepting JSON. **This is a content-type mismatch — the endpoint likely fails unless the backend also accepts form data, which it does not appear to.** (Note: the endpoint parameter is `data: IngestUploadRequest` which expects JSON, but the frontend sends multipart form data.)

## Identified Issues

### CRITICAL: Frontend URL Mismatches

1. **Graph page calls wrong URL:** `frontend/src/features/graph/useGraph.ts` calls `/api/v1/graph` but the backend route is `/api/v1/ingest/graph`. The frontend will get a 404.

2. **Search page calls wrong URL:** `frontend/src/features/search/useSearch.ts` calls `/api/v1/search` but the backend route is `/api/v1/ingest/search`. The frontend will get a 404.

### HIGH: Content-Type Mismatch on Upload

3. **Ingest upload endpoint mismatch:** The frontend `uploadFile()` sends multipart FormData to `/api/v1/ingest/upload`, but the backend endpoint signature is `data: IngestUploadRequest` (JSON body). This will fail with a validation error unless the backend also accepts form data (which it does not appear to).

### MEDIUM: Response Type Mismatch

4. **Jobs list type mismatch:** `useIngest.ts` expects `IngestJobOut[]` from `/api/v1/ingest/jobs` but the backend returns `{"items": [...], "total": N}`.

### MEDIUM: Missing Request Schema

5. **Workspace update uses raw dict:** `update_workspace` accepts `data: dict` with no Pydantic validation, relying on a hardcoded allowed-fields set. This is fragile.

### LOW: Loose Schema

6. **Feedback create has no RBAC on read endpoints:** `list_feedback` and `get_feedback` only require `TenantContext` (any authenticated user), not a specific role minimum. Any member can read all feedback in the workspace.

### LOW: Unused Endpoints

7. **14 endpoints have no frontend consumer** (marked as admin/tooling or not-yet-implemented in the UI).
