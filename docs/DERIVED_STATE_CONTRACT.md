# Derived State Contract
**Phase**: M-ARCH — Memory Architecture Freeze Gate
**Status**: PROPOSED — requires review and approval before implementation
**Created**: 2026-09-10

---

## 1. Purpose

This contract defines which data in SwarmVault is **authoritative** (source of
truth), which is **derived** (computed from authoritative data), and which is
**ephemeral** (rebuilt on demand).

This distinction is critical for:
- Cache invalidation (derived data can be rebuilt)
- Backup/restore (only authoritative data must be persisted)
- Audit (only authoritative changes create audit events)
- Recovery (derived data can be regenerated; authoritative data cannot)

---

## 2. Data Classification

### 2.1 Authoritative Data

| Data | Table/Store | Why Authoritative |
|------|------------|-------------------|
| Raw ingested content | `sources` | First human/agent-authored record of knowledge |
| Normalized messages | `normalized_messages` | Parsed representation of raw content |
| User accounts | `users` | Identity source |
| Workspace/project structure | `workspaces`, `projects`, `workspace_members` | Organizational source |
| Extracted facts | `facts` | LLM extraction of structured knowledge |
| Extracted decisions | `decisions` | LLM extraction of commitments |
| User-created memories | `memories` (user scope) | Direct human assertion |
| Agent-created memories | `memories` (agent scope) | Direct agent assertion |
| API keys | `api_keys` | Credential source |
| Policies | `policies`, `policy_versions` | Authorization source |
| Audit events | `audit_events` | Append-only historical record |

### 2.2 Derived Data

| Data | Table/Store | Derived From | Rebuildable? |
|------|------------|--------------|-------------|
| M1 session summary | `extra_metadata` on `sessions` | M1 pipeline on messages | YES |
| M4 graph nodes | `graph_nodes` | M4 extraction from facts | YES (from facts) |
| M4 graph edges | `graph_edges` | M4 extraction from facts | YES (from facts) |
| M5 retrieval scores | Computed at query time | Facts + decisions + scoring | YES (always recomputed) |
| Retrieval context pack | LLM prompt string | M5 results + query | YES (always recomputed) |
| Session title | `sessions.title` | M1 pipeline or first message | YES |
| Dashboard statistics | Computed at query time | Count queries on facts/memories/etc. | YES |
| Content hash | `sources.content_hash` | SHA-256 of raw content | YES (from source content) |
| Entity/topic lists | `sources.entities`, `sources.topics` | M1 pipeline | YES |
| Message count | `sources.message_count` | Count of normalized_messages | YES |
| LLM usage stats | `message_provenance` | LLM API response | YES (from metadata) |
| Feedback counts | Computed at query time | `message_feedback` table | YES |
| Confidence scores (M2) | `facts.confidence`, `decisions.confidence` | M2 LLM extraction | PARTIAL (LLM-dependent) |
| Authority scores | `facts.authority`, `decisions.authority` | Source configuration | PARTIAL (requires source config) |
| Embedding vectors | `memories.embedding` | Embedding model | YES (from content) |
| Temporal status (M3) | `facts.temporal_status`, etc. | Supersession logic | PARTIAL (requires re-running M3) |

### 2.3 Ephemeral Data

| Data | Location | Lifetime | Why Ephemeral |
|------|----------|----------|---------------|
| LLM provider instance | `app/services/llm.py` | Process lifetime | In-memory object |
| Policy engine cache | `app/services/policy/engine.py` | Process lifetime | Loaded at startup |
| Memory service cache | `app/services/memory.py:_cache` | Process lifetime | Performance optimization |
| Rate limiter state | `app/middleware/rate_limit.py` | Process lifetime | In-memory counters |
| Audit event buffer | `app/services/audit/` | Process lifetime | Buffered before flush |
| IngestJob queue | `ingest_jobs` table | Until processed | Queue only — not yet processed |
| Streaming SSE connections | Server memory | Connection lifetime | In-flight only |
| Chat session state | Server memory | Request lifetime | Request-scoped |

## 3. Rebuildability Rules

### 3.1 Fully Rebuildable

Derived data marked YES above can be regenerated by re-running the pipeline:

```
Re-ingest source content
  → Re-run M0 (normalize)
  → Re-run M1 (session understanding)
  → Re-run M2 (fact/decision extraction)
  → Re-run M3 (temporal supersession)
  → Re-run M4 (graph construction)
  → Overwrite derived tables
```

**Authoritative data preserved**: Source content, normalized messages, user-created
memories, audit events.

**Derived data replaced**: Facts, decisions, graph nodes/edges, session summaries,
entity lists, content hashes.

**Not replaced**: Memory records created by users or agents (these are authoritative
even though they may overlap with pipeline output).

### 3.2 Partially Rebuildable

| Data | Rebuildable? | Caveats |
|------|-------------|---------|
| Confidence scores | PARTIAL | Requires same LLM model + prompt |
| Authority scores | PARTIAL | Requires source config |
| Temporal status | PARTIAL | Requires re-running M3 supersession logic |
| Embedding vectors | YES | Requires same embedding model |

### 3.3 Not Rebuildable

| Data | Why Not |
|------|---------|
| Audit events | Append-only — new events added, old ones never modified |
| User feedback | User-submitted — cannot be regenerated |
| API key hashes | Security credentials — must be preserved |
| Message provenance | Links specific retrieval to specific responses |

## 4. Cache Invalidation Rules

### 4.1 Memory Service Cache

```python
# app/services/memory.py

class MemoryService:
    _cache: dict[str, MemoryRecord] = {}

    async def get(self, session, memory_id):
        if memory_id in self._cache:
            return self._cache[memory_id]
        record = await self._load_from_db(session, memory_id)
        if record:
            self._cache[memory_id] = record
        return record

    async def invalidate(self, memory_id):
        """Invalidate cache entry after write."""
        self._cache.pop(memory_id, None)
```

**Rule**: Any CREATE, UPDATE, SUPERSEDE, INVALIDATE, DELETE, ARCHIVE on a memory
MUST call `invalidate()` on that memory_id before returning.

### 4.2 Policy Engine Cache

```python
# app/services/policy/engine.py

class PolicyEngine:
    _loaded_at: datetime
    _policies: list[dict]

    def reload(self):
        """Force reload policies from database."""
        self._policies = self._load_from_db()
        self._loaded_at = datetime.now(timezone.utc)
```

**Rule**: Policy engine MUST reload when:
1. A policy is created/updated/deleted (emitted as event → triggers reload)
2. Periodic interval (default: 5 minutes) — for rolling deployments

### 4.3 Retrieval Cache

No retrieval cache exists currently. If one is added:

**Rule**: Invalidate on:
1. Any memory CREATE, UPDATE, SUPERSEDE, INVALIDATE, DELETE affecting the workspace
2. Any graph edge change
3. TTL expiry (default: 60 seconds for hot queries)

## 5. Backup Requirements

### 5.1 Authoritative Data (Must Back Up)

| Table | Backup Frequency | Retention |
|-------|-----------------|-----------|
| `sources` | Every 6 hours | 90 days |
| `normalized_messages` | Every 6 hours | 90 days |
| `users` | Daily | Indefinite |
| `workspaces` | Daily | Indefinite |
| `projects` | Daily | Indefinite |
| `workspace_members` | Daily | Indefinite |
| `facts` | Every 6 hours | Indefinite |
| `decisions` | Every 6 hours | Indefinite |
| `memories` | Every 6 hours | Indefinite |
| `audit_events` | Daily | 7 years (compliance) |
| `message_provenance` | Every 6 hours | 90 days |
| `api_keys` | Daily | Until rotation |
| `policies` | Daily | Indefinite |
| `graph_nodes` | Every 6 hours | Indefinite |
| `graph_edges` | Every 6 hours | Indefinite |

### 5.2 Derived Data (Can Be Rebuilt)

| Table | Backup? | Rebuild Method |
|-------|---------|---------------|
| `sessions` | NO | Rebuilt from `normalized_messages` grouping |
| `messages` (chat) | YES | User-authored — authoritative for chat history |
| `message_feedback` | YES | User-submitted |
| `ingest_jobs` | NO | Re-created on next ingest |

### 5.3 Ephemeral Data (Never Backed Up)

| Data | Reason |
|------|--------|
| In-memory caches | Rebuilt on restart |
| SSE connections | Transient |
| Rate limiter state | Rebuilt on restart |
| Audit buffer | Flushed to DB |

## 6. Pipeline Idempotency

### 6.1 Content Hash Deduplication

The pipeline uses SHA-256 content hashing to prevent duplicate ingestion:

```python
content_hash = hashlib.sha256(data.content.encode("utf-8")).hexdigest()
existing = await db.execute(
    select(Source).where(
        Source.workspace_id == tc.workspace_id,
        Source.content_hash == content_hash,
    )
)
```

**Current**: Works for `upload_and_ingest()` endpoint.
**Gap**: Does NOT work for `legacy_start_ingest()` — no content hash on IngestJob.

### 6.2 Idempotency Keys

No idempotency key mechanism exists. Retrying a failed ingestion creates a new
source record.

**Contract**: All write endpoints MUST accept an optional `Idempotency-Key` header.
If the same key is received within 24 hours, return the original response.

## 7. Consistency Guarantees

| Operation | Consistency Level | Guarantee |
|-----------|------------------|-----------|
| CREATE memory | Strong | Visible to subsequent reads in same transaction |
| SUPERSEDE memory | Strong | Old memory immediately marked SUPERSEDED |
| DELETE memory | Strong | Memory immediately excluded from queries |
| Ingest pipeline | Eventual | Facts visible after commit; not visible during pipeline |
| Graph update | Eventual | Edges rebuilt after pipeline commit |
| Cache read | Eventual | May serve stale data up to cache TTL |
| Policy reload | Eventual | May serve stale policy up to reload interval |
