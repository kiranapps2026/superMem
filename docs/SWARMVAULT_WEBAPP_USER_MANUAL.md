## 1. What is SwarmVault?

### 1.1 Purpose

SwarmVault is an AI-powered knowledge management platform designed to capture, organize, and retrieve the collective intelligence generated by AI coding sessions and conversations. It solves the problem of AI context loss: conversations with AI assistants are ephemeral, but the knowledge they produce is valuable.

### 1.2 What Problem Does It Solve?

Every time you have a conversation with an AI coding assistant (like Claude Code or similar tools), important decisions, facts, and context are generated. These disappear when the session ends. SwarmVault captures that knowledge and makes it searchable, structured, and persistent.

### 1.3 Who Is It For?

- **Individual developers** who want to maintain persistent knowledge from AI sessions
- **Teams** who need shared workspace knowledge
- **Organizations** requiring audit trails and provenance for AI-assisted decisions

### 1.4 Key Concepts

| Term | Definition |
|------|-----------|
| **Workspace** | A collaborative space within a tenant. Contains projects and members. |
| **Project** | A knowledge container within a workspace. Groups related sessions, memories, and data. |
| **Session** | A conversation context. Created during chat or imported via ingestion. |
| **Memory** | An extracted/persisted knowledge unit (M0-M5 pipeline). |
| **Source** | An ingested conversation or document. The raw input to the pipeline. |
| **Fact** | An extracted factual statement (subject-predicate-object). |
| **Decision** | An extracted decision record from a conversation. |
| **Provenance** | The evidence chain linking an AI answer back to its source memories. |
| **Ingestion** | The process of importing raw conversations into the knowledge base. |

### 1.5 What Persists Where

| Data | Storage |
|------|---------|
| User accounts, workspaces, projects | PostgreSQL database |
| Knowledge (memories, facts, decisions, graph) | PostgreSQL database |
| Sessions and messages | PostgreSQL database |
| Uploaded files | Local filesystem (content-addressed) |
| Auth tokens | Browser localStorage (`sv_tokens` key) |

## 2. Architecture Overview

### 2.1 System Components

```
┌─────────────────────────────────────────────────────────────────┐
│                        SwarmVault WebApp                        │
├──────────────┬──────────────────────────────────────────────────┤
│   Frontend   │  Next.js 15 + React + TypeScript + Tailwind CSS  │
│   (Port 3000)│  Client-side SPA with SSR capability             │
├──────────────┼──────────────────────────────────────────────────┤
│   Backend    │  FastAPI + SQLAlchemy 2.0 (async) + PostgreSQL  │
│   (Port 8000)│  97 API endpoints, JWT auth, RBAC, SSE streaming │
├──────────────┼──────────────────────────────────────────────────┤
│   Database   │  PostgreSQL with Alembic migrations (12 files)   │
│              │  Multi-tenant: tenant > workspace > project      │
├──────────────┼──────────────────────────────────────────────────┤
│   Pipeline   │  M0-M5 Knowledge Pipeline:                       │
│              │  M0: Normalization  M1: Session Understanding    │
│              │  M2: Fact/Decision  M3: Temporal Truth           │
│              │  M4: Knowledge Graph M5: Retrieval & Intelligence│
├──────────────┼──────────────────────────────────────────────────┤
│   Connectors │  7 format parsers: ChatGPT, Claude, Claude Code, │
│              │  Generic JSON, JSONL, Markdown, Text             │
├──────────────┼──────────────────────────────────────────────────┤
│   Storage    │  Local filesystem (content-addressed,            │
│              │  workspace-scoped, max 50MB per file)            │
└──────────────┴──────────────────────────────────────────────────┘
```

### 2.2 Data Hierarchy

```
Tenant (organization)
  └── Workspace (collaborative space)
       ├── Members (users with roles)
       ├── Projects (knowledge containers)
       │    ├── Sources (ingested conversations)
       │    ├── Sessions (chat conversations)
       │    ├── Memories (extracted knowledge)
       │    ├── Facts (extracted facts)
       │    ├── Decisions (extracted decisions)
       │    ├── Graph (nodes + edges)
       │    └── Provenance (audit trail)
       └── API Keys (programmatic access)
```

### 2.3 Authentication Flow

```
Register → JWT (access 60min + refresh 30d) → API requests → Refresh → Logout
```

Tokens stored in browser localStorage (`sv_tokens`). Access tokens are used in the `Authorization: Bearer` header. Refresh tokens rotate on each use.

### 2.4 RBAC Roles

| Role | Level | Permissions |
|------|-------|-------------|
| Owner | 1000 | Full workspace control, delete members, delete memories |
| Admin | 500 | Manage members, projects, API keys |
| Member | 100 | Create/edit projects, ingest, chat, storage upload |
| Viewer | 50 | Read-only: view projects, memory, chat |

## 3. Getting Started

### 3.1 System Requirements

| Requirement | Specification |
|-------------|---------------|
| Browser | Modern browser (Chrome, Firefox, Edge, Safari) |
| JavaScript | Enabled (required for SPA) |
| Screen Resolution | 1024x768 minimum (desktop recommended) |
| Backend | FastAPI server running on port 8000 |
| Database | PostgreSQL (managed by backend) |

### 3.2 Registration

**Route:** `/auth/register`
**Status:** IMPLEMENTED

1. Navigate to the SwarmVault URL
2. Click "Create one" on the login page
3. Fill in the registration form:
   - **Full name** — Your display name (optional)
   - **Email** — Your email address (required, unique)
   - **Workspace name** — Name for your workspace (required)
   - **Password** — Minimum 8 characters (required)
   - **Confirm password** — Must match password (required)
4. Click "Create account"

**What happens:**
- A new tenant is created
- A workspace is created within that tenant
- A user account is created with the Owner role
- JWT access token (60min) and refresh token (30d) are issued
- You are redirected to the Dashboard

**API:** `POST /api/v1/auth/register`
**Response:** `201 Created` — `TokenResponse` with `access_token`, `refresh_token`, `user`

### 3.3 Login

**Route:** `/auth/login`
**Status:** IMPLEMENTED

1. Navigate to the SwarmVault URL (auto-redirected from `/`)
2. Enter your email and password
3. Click "Sign in"

**What happens:**
- JWT tokens are issued and stored in localStorage
- You are redirected to the Dashboard

**API:** `POST /api/v1/auth/login`
**Response:** `200 OK` — `TokenResponse`

### 3.4 Session Management

- **Access token:** Valid for 60 minutes. Automatically refreshed via the `/api/v1/auth/refresh` endpoint when expired.
- **Refresh token:** Valid for 30 days. Rotated on each refresh (old token revoked).
- **Logout:** Revokes the current refresh token and clears localStorage. Navigate to Settings → click "Logout".

### 3.5 First-Time User Journey

```
Landing Page (/) → Auto-redirect → Login (/auth/login)
  → Sign in → Dashboard (/dashboard)
  → Click "New Project" → Enter project name → Project created
  → Click project → Project Detail (/projects/{id})
  → Navigate to Chat → Start conversation
  → Navigate to Ingest → Upload conversation → Knowledge extracted
  → Navigate to Memory → View extracted knowledge
```

## 7. Chat & AI

**Route:** `/projects/{id}/chat`
**Status:** IMPLEMENTED

### 7.1 Purpose

AI-powered chat grounded in project memory. Responses are generated using retrieved memories as context.

### 7.2 Chat Interface

| Element | Description |
|---------|-------------|
| Header | "AI Chat" title, "Grounded in project memory" subtitle, back button |
| Message area | Scrollable list of user/assistant messages |
| User messages | Right-aligned, accent-colored bubbles |
| Assistant messages | Left-aligned, secondary background with border |
| Sources panel | Shows evidence sources when memories are retrieved |
| Composer | Textarea + Send button |
| Evidence modal | "Why this answer?" button opens provenance details |

### 7.3 How Chat Works

```
User types message
  → POST /api/v1/chat/stream (SSE)
    → Backend retrieves relevant memories (M5)
    → Backend sends "sources" event (memory references)
    → Backend streams "token" events (incremental text)
    → Backend sends "done" event (final metadata)
  → Frontend renders streaming response
  → User can click "Why this answer?" for provenance
```

### 7.4 SSE Events

| Event | Data | Description |
|-------|------|-------------|
| `sources` | `{ type: "sources", sources: [...] }` | Retrieved memory references with scores |
| `token` | `{ type: "token", content: "..." }` | Incremental text chunk |
| `done` | `{ type: "done", message_id, session_id, usage, latency_ms }` | Final metadata |
| `error` | `{ type: "error", detail: "..." }` | Error occurred |

### 7.5 Chat Features

- **Streaming responses:** Real-time text generation
- **Memory grounding:** Responses reference project memories
- **Source attribution:** "Why this answer?" button shows evidence
- **Session creation:** New sessions created automatically on first message
- **Keyboard:** Enter to send, Shift+Enter for new line
- **Loading indicator:** "Thinking..." with spinner

**API:** `POST /api/v1/chat/stream`
**Request:** `{ "message": "string", "session_id"?: "string", "project_id"?: "string" }`
**Response:** `text/event-stream`

## 8. Ingestion

**Route:** `/projects/{id}/ingest`
**Status:** IMPLEMENTED

### 8.1 Purpose

Import AI conversations and documents into the knowledge base for processing through the M0-M5 pipeline.

### 8.2 Supported Formats

| Format | source_type | Description |
|--------|------------|-------------|
| Plain Text | `text` | Raw text content |
| ChatGPT Export | `chatgpt` | JSON with `mapping` field |
| Claude Export | `claude` | JSON with `chat_messages` or `conversations` |
| Claude Code | `claude-code` | JSONL with user/assistant/tool/system events |
| JSONL | `jsonl` | Line-delimited JSON messages |
| Markdown | `markdown` | Markdown formatted text |
| Generic JSON | `json` | Array of message objects |

### 8.3 Upload Methods

**Text Upload:**
1. Select source type from dropdown
2. Enter title (optional)
3. Paste content into textarea
4. Click "Upload & Process"

**File Upload:**
1. Click file picker
2. Select file (`.txt`, `.json`, `.jsonl`, `.md`, `.csv`)
3. File is uploaded and processed automatically

### 8.4 Processing Status

| Status | Icon | Description |
|--------|------|-------------|
| Queued | FileText (gray) | Waiting to process |
| Processing | Loader (blue, animated) | M0-M5 pipeline running |
| Completed | CheckCircle (green) | Successfully ingested |
| Failed | XCircle (red) | Error during processing |

### 8.5 Deduplication

If identical content (same SHA-256 hash) is uploaded again, the existing source is returned without reprocessing.

**API:** `POST /api/v1/ingest/upload`
**Request:** `{ "project_id": "string", "source_type": "string", "content": "string", "title"?: "string" }`
**Response:** `201 Created` — `IngestUploadResponse`

**Sources List:** `GET /api/v1/ingest/sources?project_id={id}&limit=50`

## 21. Security

### 21.1 Authentication

- JWT-based with 60-minute access tokens
- 30-day refresh tokens (rotated on each use)
- Tokens stored in browser localStorage
- Automatic token refresh on 401 responses

### 21.2 Authorization

- Role-based access control (RBAC)
- Four roles: owner, admin, member, viewer
- Policy engine for fine-grained permissions
- Fail-closed on database errors

### 21.3 Tenant Isolation

- All data is scoped to a workspace
- Cross-workspace access is prevented at the middleware level
- Storage keys are workspace-prefixed
- Audit events are tenant-scoped

### 21.4 Rate Limiting

- Sliding window rate limiter
- Per-IP for auth endpoints (login/register)
- Per-user for chat/ingest/search
- X-E2E header bypass available in non-production

### 21.5 Security Headers

- X-Content-Type-Options: nosniff
- X-Frame-Options: DENY
- X-XSS-Protection: 1; mode=block
- Referrer-Policy: strict-origin-when-cross-origin
- Permissions-Policy: geolocation=(), microphone=(), camera=()
- HSTS (production only)
- CSP (configured per environment)

### 21.6 Input Validation

- Pydantic schemas on all endpoints
- Content size limits on ingestion (10MB)
- Message length limits (100KB per message)
- Security sanitization of error messages

## 22. Error Handling

### 22.1 HTTP Status Codes

| Code | Meaning | User Action |
|------|---------|-------------|
| 200 | OK | — |
| 201 | Created | Resource created successfully |
| 204 | No Content | Success (delete operations) |
| 400 | Bad Request | Check input data |
| 401 | Unauthorized | Re-login required |
| 403 | Forbidden | Insufficient permissions |
| 404 | Not Found | Resource doesn't exist or was deleted |
| 422 | Validation Error | Check form fields |
| 429 | Rate Limited | Wait and retry |
| 500 | Server Error | Contact administrator |
| 503 | Service Unavailable | Backend unavailable |

### 22.2 SSE Errors

SSE streams can emit error events:
```json
{ "type": "error", "detail": "Error message" }
```

### 22.3 Client-Side Error Display

- API errors shown via `alert()` or inline error messages
- Auth errors trigger token refresh attempt
- Failed refresh clears tokens and redirects to login

## 23. Troubleshooting

### 23.1 Cannot Log In

| Possible Cause | Solution |
|----------------|----------|
| Wrong email/password | Verify credentials, check caps lock |
| Account disabled | Contact workspace owner |
| Backend unavailable | Check server status at `/health/ready` |

### 23.2 Session Expired

- The client automatically attempts token refresh
- If refresh fails, you are redirected to login
- Re-enter credentials to continue

### 23.3 Chat Not Responding

| Cause | Solution |
|-------|----------|
| No memories ingested | Ingest conversations first via Ingest page |
| Backend LLM unavailable | Check server logs |
| Network error | Check browser console, retry |

### 23.4 Ingestion Fails

| Cause | Solution |
|-------|----------|
| Invalid format | Check source type matches content |
| Content too large | Files limited to 10MB |
| Project not found | Verify project exists in workspace |

### 23.5 Search Returns No Results

- Ensure content has been ingested and processed
- Try different search terms
- Check that the project has memory items

### 23.6 Rate Limited

- Wait for the rate limit window to reset (60 seconds)
- Avoid rapid sequential requests
